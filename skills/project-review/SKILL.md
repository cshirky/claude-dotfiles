# project-review

Review the project in the current directory (or a path the user names) as
it stands, not a diff. The only file you create is the report. Don't edit,
delete or reformat anything else, even when a fix is obvious. Put the fix in
the report as a suggestion.

## 1. Mechanical scan

```
python3 -I ~/.claude/skills/project-review/scan.py <project-dir>
```

It prints JSON with an inventory (file counts and sizes by kind: code, web,
data, docs), plus candidate lists:

- `unreferenced_files`: files whose name appears in no other file
- `unreferenced_functions`: functions or classes whose name appears only
  where they're defined
- `unused_css`: classes and ids defined in CSS or `<style>` that never
  appear in markup or code
- `duplicate_files` and `near_duplicate_files` (60%+ of lines shared)
- `versioned_names`: names like `_old`, `_v2`, `copy` or `.bak`
- `function_defined_in_several_files`
- `css_selector_defined_repeatedly` and `css_identical_blocks`
- `data_files_sharing_schema`: same CSV header or JSON keys
- `markdown_broken_links` and `markdown_repeated_headings`
- `large_files_in_git` (git repos only): data files of 10 MB or more that
  are committed, sitting untracked but not ignored (one `git add .` from
  being committed), or deleted but still in history. Each is tagged against
  GitHub's 50 MB warning and 100 MB push limit, and LFS-tracked files are
  marked.
- `smells`: very long files, many inline styles, large inline scripts,
  hard-coded local paths, possible committed secrets, bare `except:`,
  committed junk such as `.pyc` and `.DS_Store`, and TODO markers

**Every list is a candidate list from name matching, not a finding.**
Verify each item before reporting it. Use `grep -rn` for the name, and read
the file when it's ambiguous. Common false positives to rule out:

- Names built at runtime: `` `badge-${x}` ``, `getattr`, `classList.add(var)`.
- Framework conventions: Observable `src/*.md` pages, Next.js `app/` routes,
  Jekyll layouts, pytest fixtures, CLI entry points in `package.json` or
  `pyproject.toml`.
- Scripts that are run by hand (data pipelines, one-off fetchers). These
  aren't dead just because nothing imports them. If the README or CLAUDE.md
  says how they're run, they're in use. If nothing documents them, report
  "undocumented" rather than "unused".
- Vendored or generated code (minified libraries, bundled CSS such as vis or
  tom-select, build output that's committed for Pages). Leave these out of
  unused-CSS and unused-function findings. Mention vendoring once if it
  matters.

Drop anything you can't confirm. A short report of real findings beats a
long one padded with guesses.

## 2. Judgment pass

The scanner can't see design. Read the project's main files: the entry
points, the largest code files, and anything CLAUDE.md or the README calls
central. Skim the rest. Look for:

- **Duplicate specifications:** the same constant, column list, color
  palette, field mapping, URL or config repeated in several places (Python
  build script and JS front end; two HTML pages with the same `<style>`
  block). Name the one that should become the source of truth.
- **Data duplication:** the same data stored twice (raw plus copy in `src/`,
  CSV plus JSON of the same table). Say which is generated from which, and
  whether the copy needs to be committed.
- **Bad design patterns:**
  - large logic blocks copy-pasted between files
  - god files that mix data loading, transformation and rendering
  - HTML generated by string concatenation without escaping
  - magic numbers scattered instead of named once
  - hard-coded absolute paths or years that will go stale
  - silent `except: pass`
  - global mutable state shared across modules
  - CSS fighting itself (`!important` chains, the same selector restyled in
    several places)
  - Markdown docs that contradict the code or each other
- **Large data in git:** for each `large_files_in_git` entry, say whether
  the file can be rebuilt from a script or downloaded from its source. If
  so, the usual response is to add it to `.gitignore` and document how to
  get it. If it must be versioned, suggest Git LFS. For files that are only
  in history, note that removing them needs a history rewrite
  (`git filter-repo`) and a force-push. Flag that as large effort and
  something for the user to decide, never a casual cleanup.
- **Stale docs:** README or CLAUDE.md describing files, commands or URLs
  that no longer exist.

Keep to what's actually there. Don't recommend frameworks, rewrites or
style preferences, and don't report a pattern unless you can point to the
lines.

## 3. Write the report

Write the report to `NOTES/project-review-YYYY-MM-DD.md` in the project root,
using today's date. Create `NOTES/` if it doesn't exist. If today's file
already exists, use `-2`, `-3` and so on rather than overwriting it.

Structure:

```markdown
# Project review: <project name>, YYYY-MM-DD

<2–3 sentences: what the project is, how big it is (from the inventory),
and the overall picture: e.g. "tidy apart from a duplicated data pipeline".>

## Summary
| Type | Findings | Suggested effort |
|---|---|---|
| Unused work | 4 | small |
| ... | | |

## Unused work
### <short title>
- **Where:** `path/file.py:120` (and others)
- **Evidence:** what you checked (e.g. "no import or call anywhere; not in README")
- **Suggested response:** delete / move to an `archive/` folder / document how it's run / keep (and why)

## Duplicates that could be merged
...
## Design patterns worth changing
...
## Docs and data hygiene
...

## Next steps
- The 3–5 changes worth doing first, in order.
- When to use the other review tools: `/simplify <files>` to apply the
  simplification findings in these files; `/code-review <path>` for a bug
  hunt in <files that looked risky>. Name real files, or leave out the
  line that doesn't apply.
```

Rules for findings:

- **Grouping:** group by type, using the four sections above. Leave out a
  section with no findings, but keep the summary table complete with zeros.
- **Location:** give each finding a file path, with a line number when it's
  specific code.
- **Suggested response:** each one is concrete and sized: delete, merge into
  X, extract Y to Z, rename, document, or keep. "Keep" is a valid response
  when something looks unused but has a reason to stay. Say so, so the next
  review doesn't flag it again.
- **Effort:** small (minutes), medium (an hour or so), or large (needs a
  plan).
- **Order:** within a section, put the most worthwhile finding first.

## 4. Tell the user

In the terminal, give the summary table, the top 3 next steps, and the full
path to the report. Don't paste the whole report.
